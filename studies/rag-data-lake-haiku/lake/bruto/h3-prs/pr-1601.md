# PR #1601: fix(body): match form content type case-insensitively in `readBody`

Mesclado em 2026-10-17. Autor: giaBaoJS.

`readBody()` decides whether to parse the body as url-encoded with a case-sensitive `startsWith("application/x-www-form-urlencoded")`. Media types are case-insensitive (RFC 9110, section 8.3.1: "The type and subtype tokens are case-insensitive."), so a request with a differently cased type falls through to `JSON.parse` and gets a 400:

```js
app.post("/", (event) => readBody(event));
```

```
$ curl -s localhost:3000 -H 'content-type: application/x-www-form-urlencoded' -d 'a=1&b=2'
{"a":"1","b":"2"}
$ curl -s localhost:3000 -H 'content-type: Application/x-www-form-urlencoded' -d 'a=1&b=2'
{"status":400,"statusText":"Bad Request","message":"Invalid JSON body"}
```

`readBody(event, { type: "formData" })` already accepts the same request, since `Request.formData()` parses the header case-insensitively, so the default path was the odd one out.

The fix lowercases the header before the check. The new test sends two differently cased form content types (one with a `charset` parameter) through the web and node matrix; without the source change both fail with `expected { status: 400, ... } to deeply equal { field: 'value', ... }`.
