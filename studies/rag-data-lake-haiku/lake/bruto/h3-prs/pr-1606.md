# PR #1606: fix(rules): keep middleware-staged headers out of `cache` entries

Mesclado em 2026-10-20. Autor: pi0x.

Fixes #1605

When global middleware runs before `routeRules()`, headers it staged on `event.res` were merged into the stored response on a cache miss. Every later hit then replayed them to every user. A staged `vary: origin`, such as from a typical CORS middleware, also stopped the response from being cached at all, because `origin` is a `Vary` name the cache isn't keyed on.

### Changes (`src/rules/cache.ts`)

- **Detach staged headers before the cached dispatch.** Before calling ocache, the wrapper takes the bag of headers already staged on `event.res` off the event, so the miss's `toResponse` can't merge them into the entry.
- **Merge them onto every response, hit or miss.**
  - Headers staged during the dispatch (`handleCacheHeaders`, moved volatile headers) still take precedence, as before.
  - On a throw or a non-`Response` result, the detached headers are put back onto the event.
  - They are not restored onto the event after a successful dispatch, because an `swr` background revalidation keeps running the handler on the same event.
- **Join `Vary` instead of replacing it.** A staged `Vary` is combined with the entry's own (e.g. from `varies`) rather than overwriting it.
- **Leave storability signals in place.** A staged `cache-control` and a wildcard `vary` stay on the event. ocache can then still refuse to store a response that middleware marked `private`/`no-store` (e.g. auth middleware on a personalized route).
- **Error headers are left untouched,** since error statuses are never stored.
- The `cors`-gated `Vary: Origin` strip in `moveVolatileHeaders` is still needed when `routeRules()` runs as route middleware: the `cors` rule then runs again inside the cached dispatch. Its doc comment now says so.

### Behavior change

On a miss, a header set by earlier middleware now wins over the same header set by the handler. That makes misses match hits, which already served the middleware's value; uncached h3 still lets the handler override it.

### Tests

- The issue's `x-user` reproduction: not served on a later hit, while each request still gets its own value.
- A route behind middleware that stages `vary: origin` is cached, and the response's `Vary` keeps the entry's `accept-language`.
- A response that middleware staged as `private, no-store` is never stored.
- `cors` + `cache` with `routeRules()` as route middleware still caches.
- Middleware-staged error headers survive a throwing cached handler.

An independent review pass caught the `private` storage and route-middleware `cors` regressions in an earlier version of this change; both are fixed here and covered by the tests above.
