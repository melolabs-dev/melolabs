# PR #1608: fix: keep middleware-staged headers out of handler-level caches

Mesclado em 2026-10-20. Autor: pi0x.

Resolves #1607

#1606 keeps middleware-staged headers out of the `cache` route rule's entries, but the logic lived in `h3/rules/cache` and used h3 internals. A route wrapped directly with ocache's `defineCachedHandler` (as Nitro's `defineCachedHandler` does) behind global middleware still leaked: on a miss, `toResponse(value, event)` merged the staged headers into the stored entry, and later hits served them to other users. A middleware staging `vary: origin` also stopped the route from being cached.

### Changes

- **New public util `withCacheIsolation(handler)`** (`src/utils/cache.ts`, exported from `h3`). It wraps a cached handler with the same isolation #1606 added:
  - Headers staged on `event.res` before the handler runs are taken off the event for the cached dispatch, then merged onto each successful response, hit or miss.
  - Staged `Cache-Control` and every staged `Vary` name except `origin` stay visible to the cache. A response that middleware marked `private`/`no-store`, or that varies on a request header the cache isn't keyed on, is therefore not stored.
  - `Vary` is joined with the entry's own rather than replaced.
  - Error responses don't get the staged success headers, matching h3.
  - On a throw or a non-`Response` result, the staged headers are put back on the event.
  - The cached handler's own properties (ocache's `invalidate`, `expire`, `resolveKeys`) are kept on the wrapper, and its type is preserved.
- **`h3/rules/cache` now uses it.** The helpers moved to `src/utils/internal/staged-headers.ts` (changed only for the `Vary` fix below); the rule-only parts (credential stripping, volatile CORS/cookie headers, the 304 rebuild) stay in the rule.

```js
import { defineCachedHandler } from "ocache";
import { withCacheIsolation, toResponse, handleCacheHeaders } from "h3";

const cached = withCacheIsolation(
  defineCachedHandler(() => "hello", {
    maxAge: 60,
    toResponse: (value, event) => toResponse(value, event),
    handleCacheHeaders: (event, conditions) => handleCacheHeaders(event, conditions),
  }),
);
app.get("/cached", cached);
```

### Behavior change in `h3/rules/cache` (fix to #1606)

#1606 hid every staged `Vary` other than `*` from the cache. That was only safe for `Vary: Origin`, whose CORS headers are isolated along with it. If middleware picked the rendered output from another request header (e.g. it read `accept-language` into the context and staged `vary: accept-language`), the entry was stored anyway and served to every language. Now only `origin` is isolated, and such routes are no longer stored unless the rule's `varies` keys on that header.

### Precedence

A header staged by middleware wins over the same header set by the cached handler, so a miss looks the same as a hit (as in #1606). One header is handled specially: a `private`/`no-store` `Cache-Control` staged by middleware is sent to the client in place of the cached handler's own (plain `handleCacheHeaders` would replace it with `public`). That way a CDN or proxy in front of the app doesn't store a page that middleware kept private, either. The `cache` rule already guarded this; `withCacheIsolation` now does too, so wrappers like Nitro's get it for free.

### Release note

Routes behind middleware that stages a `Vary` other than `origin` (e.g. i18n middleware staging `vary: accept-language`) are **no longer cached** by the `cache`/`swr` route rule, unless the rule's `varies` includes that header. Previously they were cached under one key and served to every value of the header. To keep caching them, add the header to `varies`, e.g. `{ swr: 60, cache: { varies: ["accept-language"] } }`.

### Tests (`test/cache.test.ts`, web + node)

- The issue's `x-echo` reproduction: not served on a later hit, and each request still gets its own value.
- A staged `set-cookie` is not served on a later hit.
- A route behind middleware staging `vary: origin` is cached.
- Middleware-staged `private, no-store` and `vary: *` responses are never store
