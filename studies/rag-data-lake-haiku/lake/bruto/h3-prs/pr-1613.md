# PR #1613: fix(rules): let `HTTPError.headers` opt out of `headers` rule on errors

Mesclado em 2026-10-22. Autor: pi0x.

Closes #1612

The `headers` rule applies its headers to `event.res.errHeaders` after the handler has run, and `errHeaders` takes precedence over `HTTPError.headers` (in h3's `errorResponse` and in Nitro's `createErrorHeaders`). So a handler could not change a rule header on its own error response. In Nitro (since nitrojs/nitro#4891), a 404 for a missing asset under `/build/**` got `cache-control: public, max-age=31536000, immutable`, which lets a CDN or browser cache the 404.

### Change

An `HTTPError`, thrown or returned, that carries one of the rule's keys in its own `headers` keeps that value. The rule skips the `errHeaders` write for that key only:

```ts
throw new HTTPError({ status: 404, headers: { "cache-control": "no-store" } });
// → cache-control: no-store; the rule's other headers still apply
```

### Why not detect changes to `errHeaders` (the issue's suggestion)

An earlier revision of this PR did that: it skipped keys whose `errHeaders` value changed during `next()`. A review showed that a change there isn't a reliable signal:

- **CORS helpers:** `appendCorsHeaders`/`handleCors` in user middleware (Nitro `server/middleware/`) write `errHeaders` inside the rule, so their values beat the rule on 4xx/5xx while the rule still won on 2xx. On main the rule wins both.
- **Appends:** `errHeaders.append("vary", …)` dropped the rule's `vary` on errors.
- **Nested rules:** a stacked or mounted `headers` rule needed extra tracking.
- **Opt-out mechanics:** deleting a key couldn't opt out, and returning (instead of throwing) under an inner `cache` rule didn't work.
- **Cost:** it added per-request work on the success path.

`HTTPError.headers` is an explicit statement about that error response, and the check costs nothing on successful requests.

### Unchanged (pinned by tests that pass on main and on this branch)

- 2xx responses always get the rule headers (h3js/h3-rules#5 ordering).
- `errHeaders` staged anywhere (outer middleware, the `cors` rule, CORS helpers or appends inside the rule) is still overridden by the rule on errors.
- An error `Response` the handler builds itself (e.g. an upstream 404 through `proxy`) still gets the rule header. Only `HTTPError` opts out.
- Stacked `headers` rules: the outer one wins on 2xx and on errors.

### Notes

- **`return` under a `cache` rule:** on a route that also has a `cache` rule, *return* the `HTTPError` and the `cache` rule renders it to a plain `Response` first, so the opt-out is lost. *Throwing* works.
- **Tree-shaking:** `HTTPError.isError` is inlined so that `headers`-only bundles don't pull in `error.ts` (`treeshake.test.ts` budget).
- **Nitro follow-up:** in `static.ts`, replace `event.res.headers.delete("Cache-Control")` + `throw new HTTPError({ status: 404 })` with `throw new HTTPError({ status: 404, headers: { "cache-control": "no-store" } })`.
